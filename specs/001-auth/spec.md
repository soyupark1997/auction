# 001 회원 (가입, 로그인, 권한)

상태: 확정 (열린 질문은 제안대로 확정)
단계: 로드맵 1단계

## 왜 필요한가
경매에서 "누가 올렸고 누가 입찰했는지"를 구분하려면 사용자를 알아볼 수 있어야 한다. 이후의 모든 기능(상품 등록, 입찰, 포인트)이 이 기능에 기대므로 가장 먼저 만든다. 또 "내 상품에는 입찰할 수 없다", "관리자만 강제 종료할 수 있다" 같은 규칙을 지키려면 누가 누구인지, 어떤 권한인지 서버가 판단할 수 있어야 한다.

## 사용자
- 일반 회원: 상품을 올리고 입찰할 수 있다. (한 사람이 판매자와 입찰자를 겸한다)
- 관리자: 일반 회원이 할 수 있는 것에 더해 관리 기능을 쓸 수 있다. (관리 기능 자체는 이후 단계에서 만든다)

## 기능 요구사항

### 가입
- 이메일, 비밀번호, 닉네임을 입력해서 가입한다.
- 이메일은 형식이 맞아야 하고, 이미 쓰는 이메일로는 가입할 수 없다. 대소문자만 다른 이메일은 같은 이메일로 본다.
- 닉네임은 2~20자이고, 이미 쓰는 닉네임으로는 가입할 수 없다.
- 비밀번호는 8자 이상이어야 한다.
- 가입한 사람은 일반 회원이 된다.
- 비밀번호 원문은 어디에도 저장하지 않고, 로그와 응답에도 나오지 않는다.

### 로그인
- 이메일과 비밀번호로 로그인한다.
- 성공하면, 이후 요청에서 "나"를 증명할 수 있는 증표를 받는다.
- 실패하면 이메일이 없는 건지 비밀번호가 틀린 건지 구분해서 알려주지 않는다. (계정이 있는지 알아내는 데 쓰이지 않게 하려는 것)

### 내 정보 보기
- 로그인한 사람은 자기 정보(이메일, 닉네임, 역할)를 볼 수 있다.
- 비밀번호와 관련된 정보는 어떤 경우에도 응답에 들어가지 않는다.

### 권한
- 로그인이 필요한 기능에 로그인 없이 접근하면 거절한다.
- 관리자 전용 기능에 일반 회원이 접근하면 거절한다.
- 증표가 없거나, 잘못되었거나, 유효 기간이 지났으면 로그인하지 않은 것으로 본다.

### 오류 응답
- 실패할 때는 항상 같은 모양으로 `code`, `message`, `details`를 내려준다. (기획안 15-2의 공통 형식)
- 이 기능에서 쓰는 코드: VALIDATION_FAILED(입력이 잘못됨, 400), EMAIL_TAKEN(409), NICKNAME_TAKEN(409), INVALID_CREDENTIALS(401), UNAUTHORIZED(401), FORBIDDEN(403)

## 인수 조건 (이게 되면 완성)
1. 올바른 이메일, 비밀번호, 닉네임으로 가입하면 성공하고, 응답에 이메일, 닉네임, 역할(일반 회원)이 있고 비밀번호 관련 값은 없다.
2. 이미 가입된 이메일(대소문자만 다른 것 포함)로 가입하면 EMAIL_TAKEN으로 거절된다.
3. 이미 쓰는 닉네임으로 가입하면 NICKNAME_TAKEN으로 거절된다.
4. 이메일 형식이 틀리거나, 비밀번호가 8자 미만이거나, 닉네임 길이가 맞지 않으면 VALIDATION_FAILED로 거절되고, 어느 항목이 문제인지 `details`에 나온다.
5. 올바른 이메일과 비밀번호로 로그인하면 증표를 받는다.
6. 비밀번호가 틀린 경우와 없는 이메일인 경우 모두 똑같은 INVALID_CREDENTIALS(같은 메시지)로 거절된다.
7. 증표를 가지고 내 정보를 요청하면 내 이메일, 닉네임, 역할이 나온다.
8. 증표가 없거나 잘못되었거나 만료된 채로 로그인이 필요한 기능을 요청하면 UNAUTHORIZED로 거절된다.
9. 일반 회원의 증표로 관리자 전용 기능을 요청하면 FORBIDDEN으로 거절된다. 관리자의 증표로는 통과한다.
10. 저장된 비밀번호 값은 입력한 원문과 다르다. (원문을 복구할 수 없는 형태로 저장)
11. 같은 이메일로 거의 동시에 가입 요청이 두 번 들어와도 한 번만 성공한다.

## 이 spec의 범위 밖
- 가입 시 포인트 지급 (`003-points`에서 가입과 연결한다)
- 이메일 인증, 비밀번호 재설정, 소셜 로그인
- 상품 관련 기능 (`002-auctions`)
- 관리자 전용 기능의 실제 내용 (강제 종료 등, 4단계)

## 열린 질문 (확정해야 plan을 쓸 수 있다)
1. 관리자 계정은 어떻게 만드는가? 제안: 가입 화면에서는 만들 수 없고, 개발 중에는 DB에서 직접 역할을 바꾸거나 시작용 스크립트로 한 명을 만든다.
2. 증표의 유효 기간은? 연장용 증표(갱신 토큰)를 둘 것인가? 제안: 처음엔 갱신 없이 짧은 유효 기간 하나만 둔다.
3. 로그인 시도 횟수 제한(여러 번 틀리면 잠시 막기)은 이번에 하는가? 제안: 이번에는 하지 않는다.
4. 인수 조건 9번을 확인하려면 "관리자만 접근 가능한 아무 기능"이 하나 있어야 한다. 제안: 확인용 최소 경로를 하나 두고, 4단계에서 진짜 관리 기능으로 대체한다.

## 확정된 답 (열린 질문)
1. 관리자 계정: 가입 화면에서는 만들 수 없다. 개발 중에는 시작용 스크립트 또는 DB에서 직접 역할을 바꿔서 한 명을 만든다.
2. 증표: 짧은 유효 기간 하나만 쓴다. 연장용 증표(갱신 토큰)는 이번에 쓰지 않는다.
3. 로그인 시도 횟수 제한: 이번에는 하지 않는다.
4. 관리자 권한 확인: 확인용 최소 경로를 하나 둔다. 4단계에서 진짜 관리 기능으로 대체한다.
